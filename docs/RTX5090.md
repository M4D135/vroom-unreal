## Profils préparés

| Plateforme | Configuration initiale préparée |
|---|---|
| Mac Apple Silicon | TAA, rendu interne 70 %, plafond 60 Hz, un budget d'ombres réduit. Les choix graphiques sauvegardés restent prioritaires. |
| Windows x64 | DirectX 12 SM6, ray tracing/Lumen matériel demandés, VSM et TSR natif comme base. DLSS Quality peut être choisi par défaut lorsque son runtime facultatif est réellement disponible. |
| Linux x86-64 | Vulkan SM6, ray tracing/Lumen matériel demandés, VSM et TSR natif. Cette cible n'a pas été exécutée dans cette passe. |

Les fichiers `Config/Windows` et `Config/Linux` préparent une sortie 3840 × 2160 et un plafond de 120 images/s. **Un plafond configuré ne mesure pas le débit obtenu.** Le moniteur, la VSync et les préférences sauvegardées peuvent limiter la cadence. La présence des paramètres de ray tracing ne prouve pas son activation effective ; les journaux natifs doivent la confirmer.

Les miroirs partagent une capture 512 × 128 : 30 Hz pour les effets bas et 60 Hz à partir des effets élevés. Cela augmente leur coût GPU par rapport à l'ancienne cadence de 15 Hz ; les contrôles de performance doivent inclure la vue cockpit.

## Construction et lancement Windows

Prérequis : Windows x64, Unreal Engine 5.8 et le compilateur/SDK acceptés par cette installation. Python 3.10+ est nécessaire au vérificateur, pas au simple lancement. Dans PowerShell depuis le clone :

```powershell
.\Tools\build_windows.ps1 -EngineRoot 'C:\Program Files\Epic Games\UE_5.8' -Configuration Development
.\Tools\run_windows.ps1 -ExpectedVersion 0.30.0 -Windowed
```

Le build conserve les assets versionnés et écrit `Saved/Packages/Win64/vroom-build.json` après un résultat UAT réussi. Ce manifeste contient la version, la configuration, le chemin et le SHA-256 du **binaire natif**, ainsi que les empreintes de `Source`, `Config` et `Content`. Le lanceur attend le processus du jeu directement, pas seulement le petit exécutable de lancement Unreal.

`-Mode Editor` prépare uniquement l'éditeur. `-Mode Assets` régénère explicitement les assets, y compris ceux du décor. `-Configuration Shipping` prépare une distribution Shipping ; la suite de mesure exige Development pour conserver les journaux et le profileur CSV. Les scripts PowerShell ont été relus sur Mac, **pas exécutés ni analysés par un PowerShell Windows**.

## Captures et mesure native

Choisir d'abord les options graphiques et la limite d'images/s dans le jeu. Le vérificateur fixe une fenêtre DX12 à la résolution demandée ; il ne change pas silencieusement les préférences graphiques. Il demande un bureau Windows interactif : une session SSH sans bureau graphique ne remplace pas ce contrôle.

```powershell
# Captures cockpit, voitures, options et quatre scénarios de collision.
.\Tools\verify_windows.ps1 -ExpectedVersion 0.30.0

# Même contrôle, puis 1800 images affichées avec temps CPU/GPU et trace caméra.
.\Tools\verify_windows.ps1 -ExpectedVersion 0.30.0 -Profile -TargetFPS 60

# Objectif 120 Hz, DLSS Quality exigé, puis roulage prolongé des six circuits.
.\Tools\verify_windows.ps1 -ExpectedVersion 0.30.0 -Profile -Soak -TargetFPS 120 -ExpectedDLSS quality
```

Les captures et mesures sont **affichées à l'écran**. Aucune capture d'image n'est demandée pendant une mesure CSV. Les fichiers sont conservés dans `Saved/Validation/v<version>/<date>-windows`, avec `results.json`, captures PNG, journaux complets et CSV bruts. Les captures nécessitent encore une revue visuelle humaine : la réussite d'un script ne certifie pas le dessin des mains ou la lisibilité du décor.

La suite refuse les sources/assets modifiés depuis le build, une version runtime différente, un GPU sélectionné ne contenant pas `RTX 5090` ou un RHI DX12 non confirmé. `-ExpectedGPU` permet une autre carte explicitement. Le GPU **sélectionné** est extrait de l'identifiant d'adaptateur Unreal, pas simplement d'une liste de cartes présentes. La résolution PNG est vérifiée, puis la résolution réelle des mesures est contrôlée dans les métadonnées CSV.

Le rapport conserve les lignes GPU/pilote/SM/RHI/ray tracing/DLSS et les réglages appliqués par le jeu. `-ExpectedDLSS native`, `dlaa`, `quality`, `balanced` ou `performance` exige le mode effectif rapporté après le contrôle de l'API NVIDIA. Le défaut `any` enregistre le résultat sans exiger DLSS. Il ne confond pas installation d'un plugin et activation. Pour une comparaison, sélectionner le mode dans le jeu puis réaliser **deux exécutions séparées** avec les attentes correspondantes.

## Critères explicites

Après 120 images d'échauffement, les seuils par défaut sont :

| Objectif | Moyenne minimale | 99e centile maximal | Image maximale | Fraction au-dessus de 20 ms |
|---|---:|---:|---:|---:|
| 60 Hz | 59 images/s | 18 ms | 33,50 ms | 0,5 % |
| 120 Hz | 119 images/s | 9 ms | 16,84 ms | 0,5 % |

`-MinMeanFPS`, `-MaxP99Ms`, `-MaxFrameMs`, `-MaxOver20MsFraction`, `-Frames` et `-Warmup` permettent un autre protocole. **Les valeurs réellement demandées sont enregistrées dans chaque rapport**, et un échec ne relâche aucun seuil. `TargetFPS` définit ces critères ; il ne force pas le jeu à produire cette cadence.

La caméra reprend les critères partagés de `Tools/regression_gates.py` : données finies, absence de retour en arrière sur la piste, limites de variation de lacet et d'accélération angulaire. `-Soak` parcourt les six circuits avec au moins 130 secondes théoriques d'images par circuit à la cadence cible. Les temps GPU et thread du jeu doivent être présents ; une capture incomplète échoue.

Les dix tests portables `python3 Tests/windows_verification_test.py` couvrent les manifestes périmés, les empreintes modifiées, l'échappement des chemins, les arguments natifs, le GPU effectivement choisi et le repli DLSS. Ils ne lancent pas Windows, PowerShell ou Unreal. **Les résultats natifs restent à produire.**
