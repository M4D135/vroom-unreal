**État au 20 septembre 2026 : cible Windows préparée pour la 0.34, sans build ni validation PC.** L’accès SSH à david-pc (`192.168.1.136`) a expiré et aucun environnement Windows natif n’est disponible pour cette passe. Le système démarré, le GPU et l’installation Unreal n’ont pas été inspectés. Les informations matérielles antérieures restent historiques. Aucun exécutable Windows 0.34, résultat RTX 5090, DLSS ou ray tracing matériel n’est annoncé comme produit ou validé.

Les commandes ci-dessous ciblent **0.34.0 après sa construction effective** ; le vérificateur refuse un checkout, un manifeste ou un exécutable d’une autre version. Le [guide Windows](WINDOWS.md) détaille les prérequis, la construction Development, le ZIP et le premier lancement. La validation Mac 0.34 reste distincte des preuves Windows à produire.

## Profils préparés

| Plateforme | Configuration initiale préparée |
|---|---|
| Mac Apple Silicon | TAA, rendu interne 70 %, plafond 60 Hz, un budget d'ombres réduit. Les choix graphiques sauvegardés restent prioritaires. |
| Windows x64 | DirectX 12 SM6, ray tracing/Lumen matériel demandés, VSM et TSR natif comme base. DLSS Quality peut être choisi par défaut lorsque son runtime facultatif est réellement disponible. |
| Linux x86-64 | Vulkan SM6, ray tracing/Lumen matériel demandés, VSM et TSR natif. Cette cible n'a pas été exécutée dans cette passe. |

Les fichiers `Config/Windows` et `Config/Linux` préparent une sortie 3840 × 2160 et un plafond de 120 images/s. **Un plafond configuré ne mesure pas le débit obtenu.** Le moniteur, la VSync et les préférences sauvegardées peuvent limiter la cadence. La présence des paramètres de ray tracing ne prouve pas son activation effective ; les journaux natifs doivent la confirmer.

Les miroirs partagent une capture arrière : 30 Hz pour les effets bas et 60 Hz à partir des effets élevés dans le cockpit, 10 Hz en poursuite. La vue extérieure utilise les mêmes rétroviseurs et leur reflet reste actualisé. Les contrôles de performance doivent inclure ces deux vues.

## Construction et lancement Windows

Les prérequis complets figurent dans [WINDOWS.md](WINDOWS.md#préparer-le-pc), avec la source officielle Epic pour Visual Studio et le SDK UE 5.8. Depuis PowerShell à la racine du clone :

```powershell
.\Tools\build_windows.ps1 -EngineRoot 'C:\Program Files\Epic Games\UE_5.8' -Configuration Development -CreateZip
.\Tools\run_windows.ps1 -ExpectedVersion 0.34.0 -Windowed
```

Le build conserve les assets versionnés et écrit `Saved/Packages/Win64/vroom-build.json` après un résultat UAT réussi. Le manifeste de schéma 2 contient la version, la configuration, le chemin et le SHA-256 du **binaire natif**, les empreintes de `Source`, `Config`, `Content` et `Vroom.uproject`, ainsi que celles de tous les fichiers empaquetés. `-CreateZip` demande l’archive `dist/Vroom-0.34.0-Win64-Development.zip` et son fichier `.zip.sha256`. Le dossier d’archivage doit être vide ; utiliser `-ArchiveDirectory` et `-ZipPath` pour reconstruire sans remplacer une sortie existante. Le lanceur contrôle tout le package et attend le processus du jeu directement. Ces sorties restent à produire sur Windows.

`-Mode Editor` prépare uniquement l’éditeur. `-Mode Assets` régénère explicitement les assets, y compris ceux du décor. `-Configuration Shipping` prépare une distribution Shipping ; la suite de mesure exige Development pour conserver les journaux et le profileur CSV. La syntaxe des scripts et les helpers de package ont été contrôlés avec PowerShell sur Mac ; **leur exécution native sous Windows reste non vérifiée**.

## Captures et mesure native

Choisir d'abord les options graphiques et la limite d'images/s dans le jeu. Le vérificateur fixe une fenêtre DX12 à la résolution demandée ; il ne change pas silencieusement les préférences graphiques. Il demande un bureau Windows interactif : une session SSH sans bureau graphique ne remplace pas ce contrôle.

```powershell
# Captures et scénarios 0.34 : cockpit, voitures, course, stands, drift et collisions.
.\Tools\verify_windows.ps1 -ExpectedVersion 0.34.0

# Même contrôle, puis 1800 images affichées avec temps CPU/GPU et trace caméra.
.\Tools\verify_windows.ps1 -ExpectedVersion 0.34.0 -Profile -TargetFPS 60

# Objectif 120 Hz, DLSS Quality exigé, puis roulage prolongé des six circuits.
.\Tools\verify_windows.ps1 -ExpectedVersion 0.34.0 -Profile -Soak -TargetFPS 120 -ExpectedDLSS quality
```

Les captures et mesures sont **affichées à l'écran**. Aucune capture d'image n'est demandée pendant une mesure CSV. Les fichiers sont conservés dans `Saved/Validation/v<version>/<date>-windows`, avec `results.json`, captures PNG, journaux complets et CSV bruts. Les captures nécessitent encore une revue visuelle humaine : la réussite d'un script ne certifie pas le dessin des mains ou la lisibilité du décor.

La suite 0.34 prépare **32 scénarios fonctionnels** : cinq positions de braquage, voitures et options, données et menus de course, deux sorties de piste, quatre contrôles de départ, six audits de circuit, service au stand, dépassement, trois contrôles de dérapage et six collisions. `-Profile` ajoute une mesure à la définition demandée ; `-Soak` ajoute les six parcours prolongés. Un résultat reste provisoire jusqu’à l’analyse de ses journaux, de son CSV et de sa trace caméra ; le rapport global n’est terminé qu’après tous les contrôles, y compris la stabilité des fichiers du package.

La suite refuse les sources/assets modifiés depuis le build, une version runtime différente, un GPU sélectionné ne contenant pas `RTX 5090` ou un RHI DX12 non confirmé. `-ExpectedGPU` permet une autre carte explicitement. Le GPU **sélectionné** est extrait de l'identifiant d'adaptateur Unreal, pas simplement d'une liste de cartes présentes. La résolution PNG est vérifiée, puis la résolution réelle des mesures est contrôlée dans les métadonnées CSV.

Le rapport conserve les lignes GPU/pilote/SM/RHI/ray tracing/DLSS et les réglages appliqués par le jeu. `-ExpectedDLSS native`, `dlaa`, `quality`, `balanced` ou `performance` exige le mode effectif rapporté après le contrôle de l'API NVIDIA. Le défaut `any` enregistre le résultat sans exiger DLSS. Il ne confond pas installation d'un plugin et activation. Pour une comparaison, sélectionner le mode dans le jeu puis réaliser **deux exécutions séparées** avec les attentes correspondantes.

## Critères explicites

Après 120 images d'échauffement, les seuils par défaut sont :

| Objectif | Moyenne minimale | 99e centile maximal | Image maximale | Fraction au-dessus de 20 ms |
|---|---:|---:|---:|---:|
| 60 Hz | 59 images/s | 18 ms | 33,50 ms | 0,5 % |
| 120 Hz | 119 images/s | 9 ms | 16,84 ms | 0,5 % |

`-MinMeanFPS`, `-MaxP99Ms`, `-MaxFrameMs`, `-MaxOver20MsFraction`, `-Frames` et `-Warmup` permettent un autre protocole. **Les valeurs réellement demandées sont enregistrées dans chaque rapport**, et un échec ne relâche aucun seuil. `TargetFPS` définit ces critères ; il ne force pas le jeu à produire cette cadence.

La caméra reprend les critères partagés de `Tools/regression_gates.py` : données finies, absence de retour en arrière sur la piste, limites de variation de lacet et d’accélération angulaire. `-Soak` prévoit au moins 130 secondes théoriques d’images par circuit à la cadence cible ; chaque parcours exige aussi **un tour complet confirmé dans le journal** et **7 000 échantillons caméra exploitables**. Les temps GPU et thread du jeu doivent être présents ; une capture incomplète échoue.

Les seuils 60/120 Hz ne sont pas remplacés par le budget Photoréalisme de 30 Hz mesuré sur Mac. **Les résultats natifs Windows restent à produire.**

## Contrôles de l’outillage sur Mac

Le 20 septembre 2026, **PowerShell 7.6.6 pour Mac**, provenant de l’archive officielle Microsoft dont l’empreinte a été vérifiée, a analysé sans erreur les cinq fichiers `build_windows.ps1`, `run_windows.ps1`, `verify_windows.ps1`, `windows_package.ps1` et `windows_package_test.ps1`.

Les **28 assertions sur des packages factices** passent : création et contenu du ZIP, empreinte de l’archive, inventaire complet, refus des altérations et des prérequis absents. Le journal local est `Saved/Validation/windows-034/package-fixtures.log`. Le ZIP de ce test contient des fixtures ; ce n’est pas un jeu compilé.

Les **19 tests portables** `python3 Tests/windows_verification_test.py` passent également, journal `Saved/Validation/windows-034/windows-verification.log`. Ils couvrent notamment les manifestes périmés, les fichiers du package modifiés, l’échappement des chemins, les arguments natifs, le GPU effectivement choisi, le repli DLSS, les scénarios 0.34 et le refus d’un PASS avant les contrôles de cadence et de tour complet. Ces tests Python ne lancent ni PowerShell ni Unreal.

Ces résultats valident l’outillage sur des données de test. Aucun build Unreal Windows, exécutable réel, rendu GPU, installation de prérequis Windows ou service cloud n’a été exécuté par ces contrôles. La compatibilité effective avec Windows PowerShell 5.1 et le comportement du package restent à vérifier sur Windows.
